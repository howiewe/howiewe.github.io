# docs / 開發者文件

這裡是給「之後接手寫 code 的人」看的。打開這個資料夾，幾分鐘內搞懂整個系統的長相。

## 怎麼看

- 先看 [架構總覽](架構總覽.md) = 整個系統的一頁地圖，看完知道資料怎麼流、前後端分工與有哪些主題。
- 想了解特定主題，再點進對應的檔案。

## 這份文件怎麼養（重要原則）

這些文件寫的是**這個專案的結構和職責**，不是程式碼的每個細節。

一句話總結：**文件記的是「形狀」不是「尺寸」**。形狀（幾層、各做什麼、怎麼接）才寫，尺寸（具體樣式數值、細微參數）留在程式碼裡。

### 檔案組織方式

- **按主題概念分**：依系統核心概念獨立檔案（如架構、資料庫、API、SSR前端、管理工具），不按程式碼資料夾死板硬套。
- **隨專案演進更新**：新增重要模組就加新檔，並**同步更新下方的「地圖」**，保持入口完整。
- **不堆積過時資訊**：過時就直接改成現在的樣子（不疊新的上去）、不寫 changelog（那是 git log 的工作）。
- **動態調整結構**：概念變大就拆、兩份重疊就合、沒用了就刪檔，並連同下方「地圖」一起維護，不留死連結。

### 撰寫規範

- **只寫結構，不寫細節**：調參數、改樣式細節不用動文件，那些留在 code 裡。
- **結構變了才更新**：新增主題、改變職責、換儲存方式或路由架構 → 才來改文件。
- **以程式碼為主**：發現文件描述與現況 code 對不上時，**以 code 為準**，並在定案時修正文件。
