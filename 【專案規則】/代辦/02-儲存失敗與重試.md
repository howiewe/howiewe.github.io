# 02 儲存失敗與重試

狀態：未開始修正；部分成功與失敗後資料處置仍待確認。基準見 [待辦索引](待辦.md)。

## 問題與影響

| 情境 | 目前行為與影響 |
| --- | --- |
| 產品儲存失敗 | 儲存函式捕捉錯誤後，外層仍關閉編輯視窗，使用者難以保留內容繼續修改或重試。 |
| 分類儲存失敗 | 顯示錯誤後仍切回分類列表，沒有留在編輯流程。 |
| 管理端圖片上傳失敗 | 上傳函式回傳 `null`，流程仍把它填入圖片 URL，並清掉新圖標記與 Blob；可能提交不完整圖片，且失去原本的重試材料。 |
| 批次部分圖片失敗 | 失敗圖片被排除後，仍提交產品；只要產品寫入成功，就顯示成功並返回後台，可能建立缺圖產品。 |
| 圖片已上傳、產品未存成 | R2 與 D1 是不同請求，沒有共同交易，可能留下沒有產品使用的圖片；直接重試也需考慮重複上傳。 |
| 批次產品寫入失敗 | 新分類在產品批次之前逐筆建立，產品失敗時，新分類仍可能留下。 |

產品更新／刪除後的 R2 清理也與 D1 分開，不能把資料庫操作成功等同整條流程完成；清理限制見 [資料庫與儲存](../docs/功能、資料與契約/資料庫與儲存.md)。

## 目標與待確認

- 讓使用者知道哪些成功、哪些失敗，失敗後保留可重試的編輯內容，成功才結束對應編輯流程。
- 批次是否允許部分產品成功、缺圖時是否一律阻擋，以及已建立分類與已上傳圖片要保留、回復或稍後清理，需先確認。
- 不以補一個成功或錯誤提示代替實際流程修正，也不為清理未完成資料而誤刪既有產品使用的圖片。

## 證據與相關入口

- [管理端](../../js/admin/admin-app.js)：`uploadImage()`、`saveProduct()` 與產品表單提交；[分類管理](../../js/admin/category-manager.js)：`saveCategory()` 與 `handleFormSubmit()`。
- [批次工作台](../../js/tools/batch-upload.js)：圖片上傳結果與最終提交；[資料層](../../functions/_lib/db.js)：`handleBatchCreateV2()`、產品寫入與刪除；[R2 工具](../../functions/_lib/r2.js)。
- 前次分析以隔離失敗回應重現產品表單、圖片與批次問題；分類切回列表由呼叫鏈確認。記憶體 SQLite 檢查曾重現批次產品失敗後留下分類。這些不能替代真實 D1／R2 與登入後瀏覽器驗證；本次只補核對程式。

## 建議方向

讓儲存結果清楚傳回發起操作的流程，依結果決定保留畫面、更新狀態或結束編輯；圖片在確認成功前保留重試材料。跨圖片、產品與分類的部分成功，依確認後的規則考慮重試、補償或清理方式，不預定唯一交易架構。

## 完成條件

- 產品與分類失敗時，表單內容可保留並成功重試；按鈕狀態能恢復，不誤報成功。
- 單張／多張圖片部分失敗、圖片成功但產品失敗、批次產品失敗等情境，結果符合已確認的處置規則。
- 重試不產生非預期重複產品或圖片；留下的圖片、分類及清理失敗有可辨識、可處理的結果。
- 使用隔離資料驗證前後端完整流程；真實整合尚未完成時不得宣稱已通過。
