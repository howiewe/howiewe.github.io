# 03 資料與分類階層驗證

狀態：未開始修正；欄位有效範圍與拒絕方式待確認。基準見 [待辦索引](待辦.md)。

## 問題與影響

- 產品資料層會把空名稱、負價格及不合法條碼送入寫入流程，沒有完整的伺服器端檢查。不能只靠表單限制，因為批次與直接 API 呼叫也能送資料。
- CSV 解析後直接建立待配對資料，未完整檢查必要欄位、解析錯誤及欄位內容；錯誤可能到配圖或提交後才被發現。
- 查詢參數只用 `parseInt()` 與預設值，負數頁碼／筆數沒有被阻擋。`limit=-1` 會被送進 SQL，SQLite 可因此取消筆數限制，分頁總頁數也可能變負數。
- 分類排序直接寫入 `parentId`，接受把自己設為父分類；分類新增／更新入口同樣缺少完整階層檢查。下游部分後代遍歷沒有循環防護，壞階層可能讓查詢無法結束。

## 目標與待確認

- 不讓不符合資料契約的輸入進入寫入與查詢，管理表單、批次及 API 的規則要一致。
- 名稱空白、價格的零／空值／負值、條碼是否必填及格式、查詢筆數上限，以及 CSV 哪些欄位必要，需核對現有資料與使用需求後確認，不自行把現況升為新契約。
- 階層不能自我包含或形成循環；另需評估父分類不存在、移到後代與批次排序互相形成循環的情境。

## 證據與相關入口

- [資料層](../../functions/_lib/db.js)：`getPaginatedProducts()`、`createOrUpdateProduct()`、`createOrUpdateCategory()`、`handleCategoryReorder()`、`handleBatchCreateV2()`；呼叫端為 [管理 API](../../functions/admin/api/[[path]].js) 與 [公開 API](../../functions/public/[[path]].js)。
- [CSV 工作台](../../js/tools/batch-upload.js) 的解析與提交；[產品管理](../../js/admin/admin-app.js) 和 [分類管理](../../js/admin/category-manager.js) 的輸入與排序。
- 前次隔離檢查確認無效產品內容、負數查詢筆數及自我父分類可進入相應資料層流程；SQL 檢查確認負 LIMIT 的效果。沒有在正式資料建立循環，也沒有完成所有不合法階層組合的驗證。本次核對程式仍有上述入口缺口。

## 建議方向

先確認最小資料規則，在伺服器入口守住底線，前端提早指出可修正的欄位。分類異動可按更新後的整體階層檢查，讀取端亦考慮對既有壞資料提供循環防護；具體共用方式由接手者評估。

## 完成條件

- 一般表單、批次與直接 API 對相同資料採一致規則；錯誤可辨識，不把錯誤數值悄悄轉成另一個有效值。
- 分類新增、修改與排序不能產生循環；錯誤請求不留下部分壞階層，讀取不因既有循環無限遍歷。
- 查詢正常及邊界筆數、CSV 缺欄位與錯誤內容都有必要驗證；有效既有資料仍可正常使用。

下載範本的條碼問題集中於 [型錄完整性與 PDF 輸出](06-型錄完整性與PDF輸出.md)，輸入規則確認後需一併對齊。
